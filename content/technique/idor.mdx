## Overview

Broken object-level authorization is an access-control failure. The application verifies that a request came from a signed-in user, then fails to verify that this user may access the *specific* record named in the request. The older term IDOR, or insecure direct object reference, describes a common way the failure appears.

An object can be an invoice, support case, user profile, document, booking, file, message, or nested resource. The identifier can be a number, UUID, filename, slug, GraphQL variable, or a value hidden in a request body. Its format does not decide security. The server-side authorization check does.

:::callout{type="important" title="Authentication is not authorization"}
A valid session proves who sent the request. It does not prove that the sender owns, manages, or may act on the requested object.
:::

OWASP calls this issue [broken object-level authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/). It is part of the broader broken-access-control family.

## Where object references appear

Start by mapping every place where a request selects an object. Do not limit the search to the last number in a URL.

- Path parameters: `GET /api/invoices/inv_1001`
- Query parameters: `GET /api/files?file_id=42`
- JSON bodies: `{"recipient_id":"usr_204"}`
- Form fields and hidden inputs
- GraphQL variables and mutation arguments
- Nested routes: `/teams/team_7/members/usr_204`
- Storage keys, filenames, download tokens, and object URLs

References also occur after an object is created. A client may receive an identifier in a list response, a location header, a link, a browser cache entry, or a WebSocket message. Treat each reference as a request for a server-side permission decision.

## Examples

### Horizontal access failure

Consider a multi-tenant billing product. An ordinary customer can view one of their own invoices:

```http
GET /api/invoices/inv_1001
Authorization: Bearer <customer-session>
```

An unsafe handler fetches the invoice by the client-supplied ID alone:

```python
# Unsafe: the query proves only that the invoice exists.
invoice = invoices.find_one({"id": invoice_id})
return invoice
```

If `inv_1002` belongs to another customer and the same session receives it, the flaw is horizontal privilege escalation. Both users have the same role. One user crossed an ownership boundary.

### Cross-tenant access failure

In a software-as-a-service application, a project manager may be allowed to read every report in their own organisation. A request such as `GET /api/reports/rpt_811` still needs to bind the report to that organisation. A lookup that ignores tenant membership can expose one company to another.

```python
# Safer: retrieve the object inside the authenticated tenant boundary.
report = reports.find_one(
    {"id": report_id, "tenant_id": current_user.tenant_id}
)
if report is None:
    raise HTTPException(status_code=404)
return report
```

The same rule applies to file downloads. A signed URL or opaque storage key should not replace an access decision if the application expects users to have different permissions.

### Write and delete failures

IDOR is not limited to reading data. A customer-service API might correctly show an agent's own drafts but let any authenticated agent update a draft through `PATCH /api/drafts/{id}`. A missing ownership or role check can allow edits, approvals, cancellations, or deletion. Write operations often have a larger business impact than a single data disclosure.

## How to recognise it in an authorized lab

Use accounts and objects that the lab provides. Begin with a normal request. Understand its expected response before changing one object reference.

:::steps
1. Capture a request for an object that belongs to the current test account.
2. Record the method, object reference, response status, and meaningful fields.
3. Identify a second permitted test object with a different owner, tenant, or role boundary.
4. Change only the object reference. Keep the session and every unrelated field unchanged.
5. Compare the response with the baseline. Check ownership fields and returned content, not only the status code.
6. Repeat separately for read, create, update, and delete flows when the lab exposes them.
:::

A `200 OK` is not proof by itself. The endpoint may return a generic success wrapper, an empty object, or the current user's data. A `403` or `404` can both be valid defensive behaviour. What matters is whether the protected object or action becomes available to the wrong principal.

Use an intercepting proxy, browser developer tools, or a small repeatable HTTP script. Preserve one clean baseline request. It makes comparisons and writeups far more reliable.

## Common mistakes and false assumptions

### "The ID is a UUID, so it is secure"

UUIDs and long random strings make guessing harder. They do not authorize access. IDs leak through lists, links, exports, logs, referrals, browser history, and normal collaboration features. A stolen or discovered UUID still requires an ownership or policy check.

### "The UI hides the button"

The UI is not the security boundary. A route may be hidden from one user while its API still accepts a direct request. Test the request path, not only the screen that generates it.

### "The list endpoint is protected"

Collection and detail endpoints often have different code paths. A filtered list can coexist with an unscoped `GET /resource/{id}`, download, update, or export endpoint.

### "One role check covers every object"

Role-based access control answers broad questions such as whether someone may use a feature. Object-level authorization adds context: which customer's file, which team's project, which user's profile, and which action on it. Many applications need both checks.

## Impact

The impact follows the object and operation. Read access can disclose personal data, financial records, internal files, API keys, or business plans. Write access can alter payment details, permissions, workflow state, or audit records. Cross-tenant exposure can affect every customer of a hosted product.

State the boundary clearly in a report. For example: "an authenticated user in tenant A can read an invoice belonging to tenant B." Avoid vague claims such as "all data is exposed" unless the evidence proves them.

## How developers prevent it

Make authorization part of the object lookup. Query by both the requested ID and the authenticated scope. For more complex policies, use a central authorization service or policy function before returning or changing the object.

- Derive the actor and tenant from the verified session, not from client-controlled fields.
- Apply the check to every method and representation, including downloads, exports, and background jobs.
- Deny by default when an object is missing or outside the allowed scope.
- Test with at least two users and two tenants. Cover read, update, and delete paths.
- Log denied decisions without placing sensitive object contents in logs.

Use opaque identifiers as defense in depth. Do not rely on them as the primary control. [CWE-639](https://cwe.mitre.org/data/definitions/639.html) describes the underlying authorization weakness.

## FAQ

:::faq
::faq-item{question="Is IDOR the same as broken access control?"}
IDOR is a common object-level form of broken access control. Broken access control also includes missing function-level checks and other authorization failures.

::faq-item{question="Can a random identifier prevent IDOR?"}
No. It can reduce casual guessing, but it cannot decide whether the requester may use an identifier they already know.

::faq-item{question="Should a secure API return 403 or 404?"}
Either can be valid. Many APIs return `404` for an inaccessible object to reduce existence disclosure. The important control is that the server does not return or modify an unauthorized object.

::faq-item{question="What should I keep in a lab writeup?"}
Keep the baseline request, the single changed reference, the response evidence, and a concise statement of the crossed authorization boundary.
:::
